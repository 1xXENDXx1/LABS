== Теоритическая часть

=== Принципы многозадачности в ОС реального времени (RTOS)

В операционных системах реального времени (RTOS) поддерживается *вытесняющая многозадачность*, что позволяет нескольким задачам выполняться логически параллельно на одном ядре. Каждая задача представляет собой отдельный поток исполнения с собственной точкой входа и обычно работает в бесконечном цикле без явного завершения.  
В однопроцессорной системе в каждый момент времени выполняется только одна задача, однако RTOS быстро переключает контекст между задачами, создавая иллюзию параллельной работы. 

Каждая задача обладает своим отдельным стеком и копиями переменных, объявленных внутри неё, что изолирует задачи друг от друга по памяти.  
RTOS использует *планировщик* (scheduler), который решает, какая задача должна выполняться в следующий момент, на основе приоритетов и состояния задач. Каждой задаче назначается определённый приоритет. Планировщик гарантирует, что задача с более высоким приоритетом, находящаяся в готовом состоянии, получит доступ к CPU раньше, чем задачи с более низкими приоритетами.

Если несколько задач имеют одинаковый приоритет, при включённом механизме распределения времени (*time slicing*) они будут по очереди получать процессорное время (метод *round-robin*) поровну.
Когда задачи находятся в состоянии ожидания (блокированы, *sleeping*) и ни одна прикладная задача не готова к запуску, RTOS исполняет специальную *Idle task* с самым низким приоритетом, чтобы CPU не оставался без работы.

RTOS обеспечивает детерминированное время переключения контекста: при возникновении более приоритетной готовой задачи текущее выполнение может быть приостановлено, сохраняется контекст (регистры процессора, указатели стека и т.п.) текущей задачи, после чего возобновляется выполнение более важной задачи. Благодаря этому механизму задачи в ОСРВ могут удовлетворять жёстким требованиям по времени отклика.

=== Взаимодействие задач через почтовые ящики (MailBox)

Для координации работы нескольких задач RTOS предоставляет средства межзадачного взаимодействия. Одним из таких механизмов является *почтовый ящик* (*mailbox*), представляющий собой специализированную очередь сообщений. Почтовый ящик позволяет одной задаче передавать данные или уведомления другой задаче асинхронно, не блокируя отправителя надолго.

RTOS, как правило, включает функции для создания почтового ящика, отправки сообщения (помещения в ящик) и получения сообщения (вынимания из ящика). Задача-отправитель может положить сообщение в почтовый ящик и продолжить работу, а задача-получатель в удобный момент прочитает это сообщение. Если на момент отправки ящик полон, RTOS либо приостановит отправляющую задачу до освобождения места, либо вернёт ошибку – поведение зависит от реализации ОС.

Аналогично, если задача пытается прочитать пустой ящик, она может блокироваться в ожидании нового сообщения или получить уведомление об отсутствии данных. Во многих реализациях RTOS почтовый ящик по сути эквивалентен *очереди длиной 1* – в каждый момент хранится не более одного сообщения.

Пока сообщение не забрано получателем, новый отправитель будет либо ждать освобождения ящика, либо перезаписывать/отклонять новое сообщение (в зависимости от ОС). Такой упрощённый почтовый ящик фактически обеспечивает *синхронную передачу данных* между задачами: отправитель и получатель чередуются, обмениваясь единичными сообщениями.

В других системах почтовые ящики могут поддерживать и буферизацию нескольких сообщений, действуя аналогично очереди FIFO. В любом случае использование *MailBox* упрощает обмен информацией между задачами, повышая модульность приложения.

=== Мьютексы для синхронизации доступа к ресурсам

При одновременном выполнении нескольких задач часто возникает необходимость совместного использования ресурсов – периферии, глобальных переменных или потоков вывода. *Мьютекс* (*mutex*, от *mutual exclusion* – «взаимное исключение») – механизм синхронизации, предназначенный для защиты разделяемых ресурсов. Мьютекс позволяет только одной задаче владеть ресурсом в каждый момент времени, предотвращая состояние гонки и некорректный параллельный доступ.

С точки зрения реализации, мьютекс можно представить как замок: когда задача хочет воспользоваться ресурсом, она *берёт* (блокирует) мьютекс, а после завершения работы – *отпускает* его. Пока мьютекс занят одной задачей, все остальные задачи, желающие получить этот ресурс, будут вынуждены ждать освобождения. Использование мьютексов гарантирует, что *критическая секция* кода выполняется атомарно по отношению к другим задачам.

Например, если две задачи пытаются одновременно записывать в общий лог или `std::cout`, без синхронизации вывод сообщений может перемешиваться или приводить к непредсказуемым результатам. Оборачивая операции вывода в мьютекс, можно добиться того, что задачи будут по очереди эксклюзивно получать доступ к `std::cout`, и их сообщения не перепутаются.

Многие RTOS (например, FreeRTOS) реализуют мьютексы с поддержкой *приоритетного наследования*: если задача с низким приоритетом удерживает мьютекс, необходимый более приоритетной задаче, приоритет первой временно повышается, чтобы избежать инверсии приоритетов.

=== Абстракции `ILed` и `IButton` для работы с GPIO

При разработке программ для микроконтроллеров на C++ полезно применять абстракции, отделяющие логику работы устройства от деталей аппаратной реализации. В рассматриваемом коде введены интерфейсы `ILed` и `IButton`, которые служат слоем абстракции над конкретными периферийными устройствами (светодиодом и кнопкой). Такой объектно-ориентированный подход является примером *Hardware Abstraction Layer* (HAL).

Задачи, работающие с интерфейсами `ILed`/`IButton`, могут вызывать высокоуровневые методы (например, `led->On()`, `led->Off()` для управления светодиодом, или `button->IsPressed()` для опроса кнопки) без необходимости знать, как именно эти действия реализованы на уровне регистров GPIO.

Основное преимущество – код основной логики работает с `IButton` как с абстрактным источником событий; при необходимости можно заменить привязку к конкретному пину или способ считывания (например, заменить физическую кнопку на эмуляцию в тестах) без изменения остального кода. Таким образом, `ILed` и `IButton` реализуют принцип *инверсии зависимостей* и облегчают сопровождение.

=== Настройка тактирования (HSI) и портов GPIO на STM32F411

Для корректной работы кода на *STM32F411* необходимо правильно инициализировать систему тактирования и порты ввода-вывода (GPIO) в соответствии с документацией STM.

==== Тактирование (HSI)

Микроконтроллер STM32F411 содержит внутренний высокоскоростной RC-генератор *HSI* (*High-Speed Internal*) фиксированной частоты 16 МГц. После сброса по умолчанию системная тактовая частота формируется от генератора HSI (`RCC_CFGR.SW = 00`) .

HSI удобен тем, что не требует внешнего кварцевого резонатора, однако он менее точен: частота может отклоняться из-за разброса параметров и температуры. Поэтому для периферии, требующей высокой точности (USB, точный baud-rate UART), часто применяют внешний генератор HSE.  

В учебных заданиях допустимо использовать HSI. Возможен также разгон частоты посредством PLL; выбор источника системной частоты осуществляется в регистре `RCC_CFGR`, поле `SW`, где `00` соответствует HSI, а состояние отражает поле `SWS`.

==== Инициализация GPIO

Первым шагом является подача тактирования на нужные порты GPIO через систему RCC. В STM32F411 порты GPIO находятся на шине AHB1, поэтому тактирование контролирует регистр `RCC_AHB1ENR`.  
Например, бит `GPIOAEN` (бит 0) включает порт A, а `GPIOCEN` (бит 2) – порт C .

После активации тактирования требуется настроить режим работы конкретных выводов:

* `GPIOx_MODER` – направление (вход, выход, альтернативная функция, аналоговый).  
* `GPIOx_OTYPER` – тип выхода (*push-pull* для LED).  
* `GPIOx_OSPEEDR` – скорость фронта.  
* `GPIOx_PUPDR` – внутренние подтягивающие резисторы (pull-up/pull-down).  

Для светодиода соответствующий бит в `MODER` устанавливается в `01` (цифровой выход); для кнопки – `00` (вход). Если кнопка замыкает вывод на землю, включается *pull-up*; если на питание – *pull-down*.

Управление и чтение:

* Запись в `GPIOx_ODR` устанавливает уровень на выходе (1 – высокий, 0 – низкий).  
* Для атомарных операций применяется `GPIOx_BSRR`.  
* Чтение состояния кнопки выполняется через `GPIOx_IDR`.  

Вся низкоуровневая настройка обычно производится *до* запуска планировщика RTOS (до `osKernelStart()` / `vTaskStartScheduler()`), чтобы задачи получили корректно настроенное окружение. Соблюдение этих требований гарантирует правильную работу аппаратных абстракций `ILed`/`IButton` и всего RTOS-приложения.



== Практическая часть

В операционных системах реального времени применяется вытесняющая многозадачность, при которой каждому потоку исполнения назначается собственный стек и приоритет. Планировщик ядра гарантирует, что задача с более высоким приоритетом, находящаяся в готовом состоянии, немедленно получает процессорное время. Когда все прикладные задачи блокированы, выполняется задача простоя. Переключение контекстов происходит детерминированно: при появлении более приоритетной готовой задачи RTOS сохраняет регистры текущего потока, восстанавливает контекст новой задачи и продолжает выполнение, обеспечивая жёсткие временные требования.

Для обмена данными между задачами используется почтовый ящик, реализующий очередь фиксированной длины один элемент. Отправитель помещает значение в ящик и немедленно освобождает процессор, тогда как получатель блокируется до появления сообщения либо до истечения тайм-аута. При заполненном ящике задача-отправитель ждёт освобождения места; если сообщение не принято, может быть возвращён код ошибки. Благодаря такому взаимодействию код, обрабатывающий кнопку, отделён от кода, управляющего индикацией, и нет необходимости в активном опросе.

Мьютекс представляет программный замок, позволяющий только одной задаче пользоваться разделяемым ресурсом. При обращении к защищённому коду поток блокирует мьютекс и удерживает его до завершения операций; другие потоки вынуждены ждать. Внутри ядра задействован механизм приоритетного наследования: если ресурс удерживает низкоприоритетная задача, а более приоритетная ожидает, система временно повышает приоритет первой, предотвращая инверсию приоритетов.

В приложении аппаратная часть отделена от бизнес-логики с помощью интерфейсов `ILed` и `IButton`. Эти абстракции скрывают детали работы с регистрами GPIO: метод `ILed::Switch` переключает состояние светодиода, а `IButton::IsPressed` возвращает текущее состояние входа. Такой уровень HAL упрощает переносимость и модульное тестирование.

Микроконтроллер STM32F411 запускается от внутреннего RC-генератора HSI на частоте 16 МГц. После сброса системный тактовый сигнал формируется именно от HSI, чему соответствует запись `00` в поле `SW` регистра `RCC_CFGR`. Перед конфигурацией портов необходимо включить их тактирование, для чего устанавливаются биты `GPIOAEN` и `GPIOCEN` регистра `RCC_AHB1ENR`. Линия `PA5` переводится в режим выхода для управления светодиодом, а линия `PC13` остаётся входом, используемым для кнопки пользователя.

=== Исходные коды и пояснения

[source,cpp]
----
class ButtonTask : public OsWrapper::Thread<2048>
{
public:
  ButtonTask(IButton& button,
             OsWrapper::MailBox<int, 1>& mailBox,
             OsWrapper::Mutex& mutex)
    : mButton(button), mMailBox(mailBox), mMutex(mutex) {}
  void Execute() override;
private:
  IButton&                   mButton;
  OsWrapper::MailBox<int, 1>& mMailBox;
  OsWrapper::Mutex&          mMutex;
};
----

Класс `ButtonTask` наследуется от шаблонного базового класса `Thread`, что автоматически выделяет для него стек объёмом две килобайта. Конструктор получает ссылку на аппаратную абстракцию кнопки, почтовый ящик длиной один элемент и мьютекс для защиты вывода в стандартный поток. Задача циклически опрашивает метод `IsPressed`, выполняет элементарную задержку десять миллисекунд для подавления дребезга и при фиксации нажатия помещает инкрементируемый счётчик в почтовый ящик. Если ящик занят, поток блокируется не более чем на сто миллисекунд, ожидая приёма предыдущего сообщения. После отпускания кнопки цикл повторяется.

[source,cpp]
----
class LedTask : public OsWrapper::Thread<2048>
{
public:
  LedTask(ILed& led,
          OsWrapper::MailBox<int, 1>& mailBox,
          OsWrapper::Mutex& mutex)
    : mLed(led), mMailBox(mailBox), mMutex(mutex) {}
  void Execute() override;
private:
  ILed&                     mLed;
  OsWrapper::MailBox<int, 1>& mMailBox;
  OsWrapper::Mutex&         mMutex;
};
----

Задача `LedTask` ожидает сообщение от `ButtonTask`. Метод `Execute` вызывает `MailBox::Get` с тайм-аутом одна секунда; при успешном получении значение счётчика выводится в консоль, а метод `mLed.Switch` выполняет аппаратное переключение пина `PA5`. Для визуального подтверждения события нажатия дополнительно формируется строка «Led Task:123123123123». Если раскомментировать вызовы `Lock` и `UnLock`, вывод будет защищён от одновременного доступа других задач.

[source,cpp]
----
extern "C" int __low_level_init(void)
{
  RCC::CR::HSION::On::Set();
  RCC::CFGR::SW::Hsi::Set();
  RCC::AHB1ENRPack<
      RCC::AHB1ENR::GPIOCEN::Enable,
      RCC::AHB1ENR::GPIOAEN::Enable
  >::Set();
  GPIOA::MODER::MODER5::Output::Set();
  GPIOC::MODERPack<
      GPIOC::MODER::MODER5::Output,
      GPIOC::MODER::MODER8::Output,
      GPIOC::MODER::MODER9::Output,
      GPIOC::MODER::MODER13::Input
  >::Set();
  return 1;
}
----

Функция ранней аппаратной инициализации выполняется до развёртывания глобальных объектов. В ней включается генератор HSI, выбирается он же как системный источник тактирования, подаётся тактирование на порты A и C, а также конфигурируются их режимы. Возврат единицы позволяет продолжить запуск программы.

[source,cpp]
----
int main()
{
  using namespace OsWrapper;
  OsWrapper::MailBox<int, 1> buttonMailBox;
  OsWrapper::Mutex           mutexIostream;
  Led<GPIOA, 5>              led1;
  Button<GPIOC, 13>          button;
  LedTask    ledTask(led1, buttonMailBox, mutexIostream);
  ButtonTask buttonTask(button, buttonMailBox, mutexIostream);
  Rtos::CreateThread(ledTask,    "LedTask",    ThreadPriority::highest);
  Rtos::CreateThread(buttonTask, "ButtonTask", ThreadPriority::normal);
  Rtos::Start();
  return 0;
}
----

В `main` создаются глобальные объекты `MailBox` и `Mutex`, а также экземпляры `Led` и `Button`, привязанные к конкретным пинам. Затем порождаются две задачи. `LedTask` получает высокий приоритет, чтобы обеспечивать минимальный визуальный отклик, а `ButtonTask` работает с нормальным приоритетом. Вызов `Rtos::Start` передаёт управление планировщику; дальнейшее исполнение определяется логикой задач.

[source,cpp]
----
class Mutex
{
public:
  Mutex() : handle(RtosWrapper::wCreateMutex(mutex)) {}
  ~Mutex() { RtosWrapper::wDeleteMutex(handle); }

  bool Lock(tTime timeout = static_cast<tTime>(1000))   /* мс */
  { return RtosWrapper::wLockMutex(handle, timeout); }

  void UnLock() { RtosWrapper::wUnLockMutex(handle); }

private:
  tMutex       mutex;
  tMutexHandle handle;
};
----

Класс `Mutex` конструирует системный объект ядра и гарантированно высвобождает его в деструкторе. Метод `Lock` поддерживает параметр тайм-аута, что предотвращает потенциальное вечное ожидание. Приоритетное наследование внедрено на уровне функций `wLockMutex` и `wUnLockMutex`, обеспечивая предсказуемое время доступа к разделяемым ресурсам.

Приведённая архитектура демонстрирует классический шаблон RTOS-приложения для STM32F4. Аппаратное окружение настраивается до старта планировщика, логика разбивается на независимые задачи, синхронизация достигается с помощью почтовых ящиков и мьютексов, а детали работы с периферией скрыты за абстракциями `ILed` и `IButton`. Такой подход обеспечивает предсказуемое время отклика, упрощает расширение функциональности и делает код переносимым между различными вариантами аппаратной платформы STM32.
